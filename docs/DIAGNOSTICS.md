## Diagnostic logging

`logging_setup.py` owns the existing logging switch and standard-stream/Qt hooks. `log_transport.py` owns one persistent daemon writer in the main process. Both the text file and console run behind its bounded queue. Producers copy bounded primitive fields and never wait for output, queue space or a shared thread pool. The writer releases the queue mutex before formatting, archiving, writing and flushing. Overflow drops log records, with cumulative process counts and the time span of loss in `logging_health`; it never drops input packets. The x86 bridge uses a separate bounded stderr writer, while its stdout input protocol retains its existing lock, JSON, newline and flush contract.

The queue admits at most 1,024 records of approximately 8 KiB including copied object overhead; 64 slots are reserved for lifecycle, error and summary records. Priority records also drop when full. Output flushes about every 250 ms. Shutdown waits at most two seconds for the worker; file objects are owned only by that daemon, so Python's handler shutdown cannot synchronously close a blocked sink. The OS may finish an already-started write after logging is disabled. Pending ordinary records are discarded on disable. Queued stream, selection and marker summaries finish in their original session before its end record, including partial intervals collected at disable or rotation. These retained records share the same queue capacity; overflow remains explicit in logging health. A new enable creates a new session and moves the previous text log to an archive on the same writer. A crash or blocked writer can leave an incomplete last batch. The shared storage policy below controls retained ordinary and manual history.

`diagnostics.py` collects separate native input, provider delivery, application gate and selection observations. Native valid-time accounting expires after 500 ms without another eye sample; application gate time records the gate's actual state at Qt delivery, separately from native receipt. Validity is a reported SDK measurement, not physical eye closure. Provider replacement is intentional sampling for Qt, not a disconnect. Basic summaries run about once per second, with their actual interval duration. Repeated identical state observations are omitted. Remaining repetitive basic events allow four records per event type per second and report suppression and reason counts. Selection state transitions, terminal records, hold outcomes and action links bypass that sampling. Counters are collected before queue admission; cumulative counters, observation-stream identity and interval index expose missing summary intervals. Trace records the fuller sequence subject to the queue and its explicit allowance.

JSONL schema version 1 uses `event`, `session_id`, `process_instance`, `event_seq`, `wall_time` with timezone, `monotonic_s` and an explicit `data` payload. Event time is captured before queueing. `data` supplies stream generations, context and attempt IDs where applicable. Sequence numbers also include text records, so a gap in JSONL alone is not proof of a dropped event. SDK timestamps keep their own source and microsecond unit; they are not subtracted from main-process time. The runtime record reports source/frozen mode and known versions; absent build revision is explicitly unknown. Structured and text files rotate after 16 MiB of payload, without ending the logical session. Structured names are `<session>.jsonl`, then `<session>.part-000001.jsonl`, and so on. Segment context can add at most 32 bounded snapshots; this overhead is separate from payload. Rotation does not reset attempts, observation identities, manual deadlines or launch-time trace allowance. Text rotation uses a same-directory move; failure preserves and appends to the source, with a two-second retry delay and visible failure.

Basic events include stream/selection summaries, gate receipt/application, delivery gaps, settings, screen mapping, dialog lifecycle, UI action origin, tracking notices and input suspension during the caregiver check. Trace adds native/provider samples, actual target bounds, selection timing, normalized track-box positions and already-computed fixation/trial results. Logging never activates or recalculates gaze-check telemetry. Native eye measurements remain actual SDK values; application eye eligibility follows the selected policy. Each `eye_gate_applied` event records that policy and its `application_gate_open` eye eligibility, independently of gaze freshness or a held selection. Offline analysis uses this explicit eligibility; older events without it retain the both-eye interpretation. Settings events include the policy and interruption duration. Generation guards remain in place. The existing invalid-gaze callback cannot distinguish SDK-invalid from nonfinite input, so it is labeled `sdk_invalid_or_nonfinite`. Notice timing stays independent of input cancellation. Settings construction and the Windows startup query are timed separately.

`bridge_connection` records the connection generation, decision (`failure`, `recovery` or `shutdown`), bounded reason, age of the last native eye-status delivery, observed process state and available exit code. Missing delivery age or exit code stays null. A closed stdout with `process_state=running` does not mean the process exited. Failure observations are captured before termination and retained for recovery; an exit code from app-requested termination cannot replace the original observation. Shutdown is a separate, explicit observation captured once before cleanup. Cleanup retries preserve that observation rather than adding another shutdown record. The offline reader exposes the latest 64 allowlisted observations in `analysis.bridge_connections` and marks truncated history.

Selection observations follow actual timer starts, restarts and cancellation boundaries, including same-target restarts and expired edge returns. Terminal records carry the surface, content-free control role, opaque attempt/context/target identities, timing reference, elapsed time, credited/discarded time and observed reason. A recording that begins during an existing attempt remains partial. `tracking_full_progress_hold` and `tracking_completed_pause_hold` preserve the two-stage policy; dropping fill credit emits `selection_credit_discarded` without ending the attempt. Hold outcomes include duration, the monotonic start of the hold, affected-eye evidence where available, retained/discarded credit and resumed/expired/cancelled outcome. Analysis separates holds whose start precedes recording coverage into `partial_hold_outcomes` and `partial_hold_duration`; their full durations are not measurements limited to the recording window. Older records without a start time have unknown hold coverage. These observations do not advance selection or relax freshness. Known UI boundaries pass explicit reasons for target departure, disabled targets, mouse intervention, stale gaze and eye-gate closure. An expired edge hold keeps its own reason when tracking recovers on the same target. Action dispatch preserves a nested handler failure even when Qt intercepts the slot exception.

Changed event ownership:

| Event | Owner and trigger | Purpose |
| --- | --- | --- |
| `selection_settings` | `SelectionObserver`, timing changes | Shared timing reference for a timer |
| `selection_state` | `GazeSelectionTimer`/observer, actual phase or attempt transition | Start/hold/phase evidence across all application and desktop selection timers |
| `selection_end` | Timer's deciding end boundary | One terminal reason and credited/discarded progress per observed attempt |
| `selection_credit_discarded`, `selection_hold_end` | Observer, credit change or end of a hold | Preserve short interruption, stage and recovery evidence in basic mode |
| `ui_action_requested`, `ui_action_returned` | `invoke_action`, around synchronous dispatch | Shared action and originating attempt identity, preserved across replacement controls; handler return is not proof of intended selection |
| `stream_summary`, `selection_summary` | Existing metrics owner, nonempty interval or final flush | Counts before sampling/admission, cumulative reason totals and missing-interval evidence |
| `segment_context` | Existing writer/sink, opening a rotated file or manual destination | Replay known settings/geometry and active-attempt context without new observations or counters |
| `persistence_recovered` | Writer, successful reopen after failure | Identify a coverage gap; failures also remain available outside the log itself |

Shared observations receive an `observation_id` before ordinary/manual fanout. Starting/stopping manual recording or rotating a file does not reset their owner. Explicit context records are not new observations. Independent Settings, Quick actions menu and precision-zoom timers use the same observer; gaze-check calculations retain their own report contract.

Typed text, suggestions, phrases, key labels and content action IDs are excluded from added events. Such actions receive random IDs local to the current context; safe control names such as `confirm:accept` remain readable. Exception snapshots retain their type and bounded frame locations, without traceback locals or exception text. Trace coordinates and target geometry can still reveal activity; these local recordings are not anonymous. Trace is explicitly enabled, lasts at most ten minutes or 32 MiB of additional records, then returns to basic logging. See [collection instructions](USER_GUIDE.md#diagnostic-log-collection) and [developer analysis](DIAGNOSTICS.md#diagnostic-log-analysis).

## Short diagnostic recordings and support packages

| Owner | Responsibility |
| --- | --- |
| `ui/diagnostic_recordings.py` (`DiagnosticRecordings`) | Application-lifetime status, start/stop requests, Qt delivery, history/export queue and the shared indicator |
| `diagnostics.py` and `log_transport.py` | Existing observations and the persistent `LogWriter`; recording admission, event order, deadlines, segment rotation and final drain |
| `diagnostic_recording.py` (`RecordingStore`) | Metadata validation, crash recovery, retention, full inspection and atomic support ZIP export |
| `ui/recording_badge.py` | One shared `RecordingIndicator` and passive `RecordingBadge` views; no recording or input decisions |
| `build_info.py` | Cached source identity shared by ordinary logs, recordings and gaze-check reports |

### Window and indicator ownership

The hotbar owns `DiagnosticRecordings`; closing the recording window keeps recording active. Opening that window suspends normal input until returning. The gaze-check shortcut is unavailable during precision/button measurement. Hiding the check for diagnostics stops its UI timer and telemetry collection without discarding its report; returning restores the check and its existing input suspension.

All badges bind to the same indicator, including windows opened later. The indicator's saved-confirmation timer and accessibility announcement identity are shared; reopening a window must not restart them. Badges reserve space or overlay an existing control, take no focus and pass mouse events through. They never move gaze targets or replace tracking/speech notices. The [collection guide](USER_GUIDE.md#diagnostic-log-collection) owns visible messages and durations; the [design workflow](UI_DEVELOPMENT.md#application-design-reference-workflow) maps their references.

### Recording admission and completion

Manual recording reuses `diagnostics.py` observations and the persistent `LogWriter` queue. The writer snapshots a recording identity with each event, so normal-log toggles cannot discard recording events or mix segments. Only structured events enter the recording; text logging and console output are excluded. Normal logging keeps its independent switch and continues while enabled. Manual trace can start without ordinary logging or a restart. It never changes saved settings, eye eligibility, input decisions, or measurement calculations.

The selected duration is 1, 2, 5 or 10 minutes (default 2); a monotonic deadline, manual stop, shutdown or write failure ends admission. There is no recording byte stop. `snimak.jsonl` continues in `snimak-000001.jsonl` and later segments under one identity. One recording remains busy through the writer's confirmed drain/close, including a blocked sink; another cannot start during that interval. Queue pressure and truncated snapshots are counted for this recording rather than copied from process-cumulative normal-log health. The last segment contains the lifecycle footer. Status distinguishes start/record/finish, end reason, lifecycle footer and completeness. Shutdown or a missing footer is incomplete even when some data was saved. No file/console wait or worker join is added to gaze/Qt callbacks. Application logging retains its existing two-second shutdown bound.

The status progresses from `starting` to `recording` to `finishing` while the writer drains. An inactive status or a present closing record alone does not establish completeness. For a `manual_trace` stream, the offline reader requires lifecycle records, no parse warnings or size-limit event, a `manual` or `time` end reason, and valid footer `recording_health` without dropped records, writer errors or bounded snapshots. Missing or invalid recording health leaves it incomplete. Process-cumulative `logging_health` remains separately reported and does not make a clean later recording incomplete. Ordinary log sessions keep their existing process-health checks.

### History, recovery and retention

`diagnostic_recording.py` owns the recording sink, atomic metadata, bounded-edge history and crash recovery. `recording_metadata.py` owns the context allowlists and metadata validation; `recording_export.py` streams support ZIPs and formats their summaries. `log_storage.py` applies the shared retention policy. `log_output.py` owns ordinary file output/rotation while `log_transport.py` keeps queue admission and writer lifecycle. The existing serial file worker runs recovery, maintenance and exports. Qt and writer callbacks never take its inspection lock. Writer finalization closes the recording and stores its final metadata without waiting for pruning or export. Reservations cover queued and running exports and release on success, failure or cancellation. A process-local registry protects active recordings and current ordinary files without holding a registry lock during file work.

`GazeSettings.log_storage_gb` persists a shared budget: 4 GB by default, integer range 1-10 GB. GB is decimal (1,000,000,000 bytes); segment bounds use MiB. Ordinary JSONL/text, all manual segments and their metadata count together. Old five-recording/200 MiB retention is removed. Oldest closed eligible items go first, with equal ordinary/manual priority; a manual recording is one item. Current output, entire active recordings and reserved exports are protected. Closed ordinary segments become eligible during long sessions.

Maintenance follows startup recovery, runs about every five seconds and is requested after budget changes. It attempts deletion of at most 128 eligible items per pass and retries on later passes. Free space on the log volume below 1 GB triggers cleanup even below budget; recovery requires 2 GB free. Protected bytes plus the two current ordinary 16 MiB files and bounded context are temporary working space, not a second retained-history allowance or a recording size cap. Active recordings can exceed the budget until they close. Actual usage, protected bytes, oldest known log time, cleanup status and pruning totals are measured independently of writer success. An unknown old timestamp stays unknown. Failed or interrupted deletion is measured again before reporting usage.

Only recognized ordinary names and recording files are managed. Supported pre-upgrade logs are included; corrupt known recordings still count. Symlinks, Windows reparse points, unknown files and unrelated content are preserved, with safety rechecked before deletion. An extra file prevents deletion of its recording folder. Exported ZIPs and gaze-check reports are excluded. Retained logs need no compression; ZIP export retains DEFLATE compression.

Persistence failures identify ordinary output, manual output or both in the existing passive reserved badge. They take precedence over countdown, finishing and saved confirmation, without moving targets or taking focus. Diagnostics shows storage and failure details plus retained gap history: affected output, reason, local start time and recovery time, or an ongoing indication. Truncation is stated when older gaps have left the latest-64 history. A successful write followed by flush, reopen or confirmed new-recording close clears the corresponding failure; starting a recording alone does not. Disabling ordinary logging hides its current warning while retaining its gap history. No timed recording is silently restarted or extended. Gap details retain the latest 64 entries and declare truncation.

A killed process can leave partial segments or initial metadata. Startup recovery labels readable remnants interrupted, with unknown duration distinct from zero, then restores the shared budget. A recovery failure preserves older data and blocks another recording until history recovery succeeds. History reads bounded metadata and file edges; full streamed analysis happens only on inspection/export. History compares the retained segment names with the declared segment count, even when the first or a middle segment is absent. Missing segments mark the recording interrupted and incomplete despite a clean footer. Partial readable recordings can be exported with `complete=false`; the manifest and summary identify missing segment indices (at most 200, with an explicit truncation flag). Mixed session/process identities and unsupported records still block export. Unsupported/unreadable recordings remain visible and cannot be exported.

### Support ZIP contents and privacy

The local ZIP includes these files; it does not copy a settings or logs folder:

| File | Contents |
| --- | --- |
| `snimak.jsonl`, `snimak-000001.jsonl`, ... | All retained segments of the chosen detailed recording |
| `kontekst.json` | Allowlisted gaze settings and environment |
| `sazetak.txt` | Readable Bosnian technical summary |
| `manifest.json` | Version 1 manifest, recording lifecycle/completeness and each payload file's byte size and SHA-256; the manifest does not hash itself |
| `provjera/rezultat.json`, `provjera/izvjestaj.txt` | Only when explicitly selected: one current-memory or saved gaze-check report, with its own date, policy, simulation flag and state |

Nothing is attached automatically or sent over the network. Payloads and SHA-256 are streamed in bounded chunks; a changed source aborts export before replacement. Export uses an adjacent temporary file and atomic replacement of the exact Windows Save As destination, without appending an extension after overwrite confirmation. Failures preserve an existing destination. Trace coordinates/geometry can reveal activity; composed/spoken text, key labels, credentials, the speech library, audio, screenshots and device serial numbers are excluded. `GAZE_KEYS` and `recording_context` in `recording_metadata.py` (also exposed by `diagnostic_recording.py`) own recording-context selection; `SETTING_KEYS` and `ENVIRONMENT_KEYS` in `tracking/gaze_check_report.py` own report context. Extend those explicit allowlists rather than serializing whole settings or device objects.

### Build identity

`build_info.py` provides one cached build identity to normal logs, recordings and gaze-check reports. Source startup resolves the Git revision and dirty state before UI work; missing Git information stays unknown. Package preparation embeds `BUILD_INFO.json` beside `VERSION`, with the full source revision and a separate dirty flag. Frozen runtime reads that file without invoking Git; the package smoke check rejects a missing/invalid revision. A dirty build is explicitly different from an exact clean revision. The runtime log-root override never changes the source used for build identity.

## Diagnostic log analysis

The [logging contract](#diagnostic-logging) owns schema, clocks, queue, privacy and rotation. The [user guide](USER_GUIDE.md#diagnostic-log-collection) owns explicit recording, ZIP export and the older launch-time trace. For source launches, set the same `POGLED_ASSIST_GAZE_DIAGNOSTICS=trace` variable before `dev.ps1 run`; that trace requires ordinary logging, unlike explicit recording.

An offline reader imports neither Qt nor a Tobii backend. It accepts an existing single JSONL or a copied log folder:

```powershell
.\.venv\Scripts\python.exe -m pogled_assist.log_reader .\logs
```

Folder input groups segments by process/session/recording and preserves separate process clocks. Stable shared observation IDs deduplicate ordinary/manual overlap, including intervals; a temporary SQLite database bounds memory for both identities and the chronological event merge. Overlapping ordinary/manual streams are merged by monotonic event time within their process, before analysing attempt/context transitions and counter intervals. The temporary database closes after analysis. No timestamp-based deduplication is attempted for old files. Context snapshots restore known references without adding observations. New ordinary sessions and manual recordings copy the context known at their admission boundary, including each retained geometry chunk. Rotation replays context without resetting shared attempts or IDs. Warning lists retain at most 200 entries and expose total/truncation. Missing, malformed, partial or concurrently removed files leave available evidence readable. Missing segments remain missing/unknown unless there is explicit pruning evidence; sequence gaps alone prove no loss. No original installation or absolute source path is needed.

It counts provider rejection reasons from summaries and selection-end reasons from events. Surface/settings outcomes, hold duration/outcomes and coverage, discarded credit, action links and cumulative reason counters accompany the existing bridge and latency evidence. The Bosnian `sazetak.txt` includes these outcomes, settings intervals, latency measurements, discarded progress, missing counter intervals, partial attempts and truncation/completeness limits. Malformed new optional identity/outcome fields produce a parse warning and skip that record; subsequent valid evidence remains available. It reports process-cumulative writer health separately from a manual recording's footer health and end reason; do not sum cumulative loss counts repeatedly. The [recording contract](#short-diagnostic-recordings-and-support-packages) defines when a recording is complete. The same command accepts a recording's `snimak.jsonl`, including one extracted from a support ZIP. Basic event counts can be lower than actual transitions; check suppressed counters in the summaries. Missing start/end, malformed or partial last lines, dropped records and size limits constrain the conclusion. Read the requested time range's raw events when explaining a specific attempt. Compare event timestamps with video time; file rotation names are not session start timestamps. Do not infer tracking accuracy without a known intended target.

For a reported selection failure:

1. Establish the app version, `build_revision`, `build_dirty`, backend, policy, timing settings and simulation flag. Old logs cannot validate a newer implementation; a dirty revision does not identify an exact clean build. Missing metadata stays unknown.
2. Check `complete`, `lifecycle_complete`, parse warnings, `session_end_reason` and the applicable health counters before interpreting event counts. A closing record proves neither loss-free data nor successful intended selection.
3. Find the time range and intended target. Follow native eye receipt, provider rejection/delivery, applied application gate and selection events in order. Application eligibility is distinct from actual both-eye validity and from fresh gaze; an eligible-eye event alone cannot confirm a selection. Older events without explicit application eligibility retain the reader's both-eye interpretation.
4. Separate observed evidence from explanations needing a new recording or target-machine check. A change of target may be intentional; it is not proof of jitter. Aggregate gaze-check reports provide measurements for their own dated attempts, not a replay of the recorded interaction. An optionally attached report may be from another time or policy.

Support ZIP hashes describe the payload files listed in the manifest. Check them when transferring a package, and keep its recording identity separate from an optional report identity. Never attach whole local data folders or raw user logs to the repository as test fixtures; use synthetic inputs.

For changes to diagnostics, test the same provider/controller/Qt input sequence with logging off, basic, trace and a blocked writer. Include the existing gaze check and tracking-feedback suites: their snapshots, coverage, interruption counts and UI state must agree. Test actual blocked file/console sinks, overflow, runtime rotation, missing streams, exceptions and bounded shutdown. Keep stdout IPC atomic and independent of droppable logging. Use the existing pytest fakes and repository verification commands; Mac-only checks are not Windows or Tobii hardware verification. Measure producer/Qt latency, CPU, memory and output size on the same reference Windows device before release. A background thread still shares Python scheduling and the GIL, so asynchronous output alone does not establish zero overhead.

The manual recording lifecycle and support ZIP use `tests/app/test_diagnostic_recording.py` and `tests/ui/test_diagnostics_e2e.py`; existing gaze-equivalence scenarios also run with manual recording. Durations and rotation use fake clocks/small bounds; a synthetic recording above 32 MiB also checks streamed inspection/export memory. History reads only bounded metadata and lifecycle edges. Full JSONL analysis and compression run during export on a file worker. These checks protect behavior and bounded work; reference-device overhead remains a separate manual measurement.
